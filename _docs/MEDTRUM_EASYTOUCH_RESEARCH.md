# Medtrum EasyTouch reactivation research

## Source artifact

- APK: `Medtrum EasyTouch mmol_L 1.4.67`
- Package: `com.medtrum.easytouchforandroidmmol`
- Local APK SHA-256: `1F7FA7C77A7835421F429BF111EC72EABBA5B0770840E3EE02E2693B1C12E1A3`
- Extracted firmware: `assets/upgrade/fm008_latest.hex`
- Firmware SHA-256: `999EFC5441E32058A03691A5572C216E19A4267FC93D2F4C09F83BC5B83A34B0`

The Android application is protected by 360 Jiagu. Static JADX output contains only the loader and
resource stubs, so the application command path is not available from its on-disk DEX files.

The Intel HEX firmware contains a PDM image at `0x90000000-0x90289EA3` (2,662,052 bytes). Its
SHA-256 is `A07A15B8743CCFFDABD06084FBEAA51F5F7DC8BF01DA3A3AC28F83870F823076`.

## Confirmed evidence

The firmware contains the following injection-controller diagnostics:

- `[INJ]connect new patch`
- `[INJ]reconnect patch:cancel operation timer`
- `[INJ]inj_jump_prime`
- `[INJ]buffer operation:%d`

This confirms that a jump-prime path exists in the PDM firmware. It does not establish the BLE
opcode, payload, valid patch states, reply format, or safety interlocks. AAPS currently defines
`PRIME=16` and `ACTIVATE=18`; opcode 17 is unused, but treating it as jump-prime is only a
hypothesis. No therapy command is added from that inference.

## Apex5 Medtrum capture

Apex5 adds an application-level Medtrum BLE trace. It records:

- connection and disconnection transitions;
- setup-wizard step and pump state;
- complete logical TX/RX messages with command name and opcode;
- every GATT write, notification, and indication chunk in hexadecimal;
- wall-clock and monotonic timestamps.

Storage is bounded to ten 2 MiB JSONL files and two exported ZIP files. Use the Share action on the
Medtrum screen to export `medtrum-ble-*.zip`. Root and a connected computer are not required for
this AAPS trace.

This trace can characterize a normal AAPS activation and future controlled driver experiments. It
cannot observe BLE traffic generated by the official EasyTouch application because Android isolates
applications. Capturing an EasyTouch session requires Android Bluetooth HCI snoop logging in
Developer options and subsequent extraction through an Android bug report/ADB, or capture on a
separate BLE sniffer. No root is normally required for the bug-report route, but device firmware can
omit the snoop file.

## Evidence required before implementation

1. Capture one complete ordinary activation and identify `PRIME`, state transitions, and `ACTIVATE`.
2. Capture the same patch-reconnect workflow that invokes jump-prime in EasyTouch/PDM.
3. Diff logical messages and verify the candidate command over more than one session.
4. Confirm accepted and rejected source states, response codes, timeout behavior, and resulting
   reservoir/session counters.
5. Implement the command behind an explicit experimental gate and initially keep it unavailable to
   automated therapy.

Reactivation must remain unimplemented until the command and state contract are observed. Sending an
unknown opcode to an insulin pump is not a valid discovery method.
