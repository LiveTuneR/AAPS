# Приемка Apex bolus safety на физическом устройстве

Статус сборки до выполнения этого протокола: `EXPERIMENTAL_DEVICE_VALIDATION_REQUIRED`.
Все сценарии подачи выполняются только OFF-BODY, на отдельной помпе, не подключенной к человеку. Этот документ не является подтверждением клинической пригодности.

## Политика безопасности

- `Completed` подтверждает только live-завершение. Доставка считается подтвержденной после совпадения с постоянной историей.
- При `DELIVERY_UNCERTAIN` запрещены ручной/Wizard/QuickWizard/Wear/SMB/extended bolus и повышающий TBR. Разрешены чтение, reconnect, reconciliation, suspend и уменьшающий/останавливающий TBR.
- Неоднозначный болюс никогда автоматически не повторяется.
- Неизвестная доставка не записывается как подтвержденные `0 U` или как точная подтвержденная доза. Она остается в журнале и блокирует дополнительный инсулин.

## Фазы

1. **A: чтение без подачи.** Подключение, статус, LatestBoluses и BolusHistory. Проверить firmware `1.1.1.0`, protocol `4.12`, identity hash и события `bolus_history_query/candidate`.
2. **B: штатный малый болюс OFF-BODY.** Убедиться в цепочке `created -> persisted -> sent -> accepted -> progress -> live_completed -> history_match -> resolved`; в БД одна запись с фактически выполненными шагами.
3. **C: разрыв связи.** Отдельно до write, после write до Accepted, после Accepted, во время progress, после Completed и во время history query. После неоднозначного write ожидается gate, отсутствие повторной команды и сохранение UUID после рестарта.
4. **D: отсутствующая история.** Если LatestBoluses не содержит дозу, должны быть две ограниченные попытки и BolusHistory. При отсутствии совпадения ожидается `DELIVERY_UNCERTAIN`, а не `0 U`.
5. **E: восстановление.** Перезапустить приложение/телефон, подключить ту же помпу и повторить reconciliation. Другая помпа не должна снять gate. Gate снимается только доказуемым совпадением, подтвержденной отменой/частичной доставкой либо доказанным отказом до write.

## Сбор свидетельств

Экспортировать 1/4/7 суток из телеметрии. ZIP должен содержать structured telemetry, manifest, обычные AAPS-логи, Apex trace и `bolus-operations.json`. Для каждого сценария записать UTC начала/конца, operation UUID, число физических `Bolus` write, состояние до/после, SHA-256 APK и ZIP.

PASS возможен только если для одного UUID был максимум один bolus-write, restart не снял uncertainty, stale-запись не стала совпадением, а подтвержденная история синхронизировалась ровно один раз. Любая повторная подача, скрытая неопределенность или самопроизвольное снятие gate означает STOP/FAIL.
